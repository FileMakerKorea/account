# ACCOUNT 서비스 기획서

버전 0.1 | 검토용 초안 | 2026년 9월 30일

## 01 기획 개요

### 목적

기존 FileMaker AccountV4의 업무를 바탕으로 수입·지출·카드·할부·예적금과 사업 매출을 관리하는 서비스의 범위와 화면, 계산 규칙을 정의한다. 빠른 입력, 일관된 월별 집계, 기존 내역 보존을 우선한다.

### 기획의 전제

사용자가 지정한 shadcn b0 · Aria · Vite와 라이트·다크 토큰을 디자인 기준으로 사용한다. 웹 UI를 기준으로 설계하되, Firebase Authentication과 Firebase Hosting은 사용자 선택으로 확정했다. Firebase 통합 방향에 맞춰 DB는 Firestore로 설계한다. FileMaker 완전 대체 여부와 은행 연동 방식은 아직 확정하지 않았다. 이 문서는 구현이나 데이터 변경을 수행한 결과가 아니다.

| 구분 | 의미 |
| --- | --- |
| 확정 | 사용자가 명시한 기획 우선 진행과 등록된 디자인 기준 |
| 관찰 | 제공 XML의 구조·계산식·스크립트에서 확인한 사항 |
| 제안 | 본 기획서에서 제시하는 신규 동작과 개선 기준 |
| 미확정 | 사용 목적 또는 실제 데이터 확인 뒤 결정할 사항 |

### 문서 구성

2장 현황과 문제 / 3장 범위와 요구사항 / 4장 화면 설계 / 5장 주요 사용 흐름 / 6장 계산 규칙 / 7장 데이터와 이관 / 8장 검수와 추진 계획 / 9장 결정 사항과 근거 / 10장 Firebase 개발환경과 예금 조회 확장

### 완료의 정의

사용자가 같은 월의 수입·지출·잔액을 일관되게 확인하고, 일반 지출과 할부를 오류 없이 입력·수정할 수 있어야 한다. 이관 대상 원본과 새 시스템의 건수·금액 차이를 설명할 수 있어야 한다.

## 02  기존 시스템 현황

관찰 기준: 2026년 9월 30일 생성된 FileMaker 보고서. 실제 거래 레코드와 실행 화면은 제공되지 않았다.

| 업무 영역 | 보고서상 레코드 | 확인된 구조 |
| --- | --- | --- |
| 가계부 | 19,255 | 지출일·귀속 연월·분류·카드·할부 연결 |
| 수입 | 98 | 사람별 고정 수입 필드와 월별 잔액 |
| 분류 | 대분류 13 / 소분류 22 | 그룹과 소분류 관리 |
| 카드 / 할부 | 11 / 65 | 카드별 합계, 회차별 지출 생성 |
| 예적금 / 사업 매출 | 58 / 19 | 만기·예상금액, 공급가액·부가세 |
| UI / Location | 1 / 291 | 화면 상태, 위치·기기 관련 기록 |

전체 구조: 기본 테이블 10개, 필드 176개, 테이블 오커런스 29개, 관계 25개, 레이아웃 25개, 스크립트 36개, 값 목록 15개. 두 XML은 같은 시스템의 요약·상세 보고서다.

### 우선 해결할 사항

① 수입 테이블의 지출총합계는 카드내역을 제외한다. UI의 지출총합계_제외는 카드내역·랍스터코드·텔레법인을 제외한다. 같은 “지출”처럼 보이는 지표의 포함 범위가 다르다.

② 할부 생성 스크립트는 연말 이후 반복 중 연도를 누적 증가시킬 가능성이 있으며, 동일 반올림 금액을 각 회차에 넣어 원금과 합계가 달라질 수 있다. 정적 분석상 위험이며 실제 발생 여부는 미검증이다.

③ UI 연월과 할부 대분류 자동입력식에 유실 필드 참조가 있다. 카드 연월에는 주석 처리된 유실 참조가 있어 활성 계산식과 구분해야 한다.

④ 카드 결제기간 필드는 있으나 확인한 카드 사용액 관계는 연도·월 기준이다. 결제예정액과 월 사용액을 같은 지표로 취급하지 않는다.

## 03  범위와 요구사항

아래 단계 구분은 제안이다. 사용자 수와 운영 범위 확인 후 우선순위를 확정한다.

| ID / 단계 | 기능 | 필수 동작 |
| --- | --- | --- |
| F01 / 1차 | 월별 현황 | 월 이동, 집계 기준 표시, 수입·지출·잔액, 제외 내역 확인 |
| F02 / 1차 | 지출 관리 | 검색·필터, 생성·수정·취소·삭제, 변경 즉시 재집계 |
| F03 / 1차 | 수입 관리 | 수입원·귀속월·금액·메모 관리 |
| F04 / 1차 | 카드 관리 | 카드별 월 사용액, 기간 표시, 연결 내역 조회 |
| F05 / 1차 | 할부 관리 | 회차 미리보기, 원금 일치, 삭제 범위 선택 |
| F06 / 1차 | 기본 설정 | 분류·집계 제외 기준, 사용자와 기본 권한 |
| F07 / 2차 | 예적금 | 납입액·원금·만기·예상금액·합산 제외 관리 |
| F08 / 2차 | 사업 매출 | 공급가액·부가세·총액, 개인 집계와 분리 |

### 대상 사용자와 권한 제안

사용자는 본인 개인용으로 실제 은행·카드 내역을 조회한다고 명시했다. 기본 사용자는 본인 한 명이며 타인·가족 공유는 현재 범위에서 제외한다. 장부와 금융 연결은 본인 UID에 귀속한다. 향후 공유 요구가 생기면 별도 권한 모델을 확장한다.

### 이번 범위에서 보류

실제 은행·카드 내역 조회는 사용자 확정 요구다. 금융 연동 제공사와 개인 이용 조건을 먼저 검증하고 구현 순서를 정한다. OCR, 자동 세무 신고, 투자 추천은 현재 범위에서 제외한다. Location의 위치·기기 수집, 은행 로그인 정보 보관, 카드 혜택 계산의 확대는 필요성을 확인한 뒤 별도로 결정한다.

### 기존 데이터 보존

2차 기능으로 분류된 데이터도 원본 보존과 이관 대상 목록에 포함한다. 운영 전환 시 2차 기능이 미완료라면 기존 시스템 조회 유지 또는 읽기 전용 제공 방법을 먼저 정한다.

## 04  화면과 디자인 설계

디자인 정본: [디자인 표준](../design/README.md) 및 [색상 토큰](../design/tokens.css). 아래 배치는 업무에 맞춘 제안이다.

| 화면 | 배치와 표시 내용 |
| --- | --- |
| 월별 현황 | 왼쪽 메뉴 → 월 선택·지출 추가 → 수입·지출·잔액 → 분류별 합계 → 거래 목록 |
| 거래 목록 | 검색, 분류·카드·기간 필터, 합계 기준, 날짜·항목·분류·카드·금액·메모 |
| 지출 입력 | 지출일·귀속월·항목·금액·대분류·소분류·카드·메모, 저장과 취소 |
| 카드 상세 | 선택 카드와 집계기간, 사용합계, 연결 거래 목록 |
| 할부 입력 | 총액·개월수·시작월 → 회차별 귀속월과 금액 미리보기 → 일괄 저장 |
| 예적금 / 매출 | 목록과 상세 입력 분리, 개인 합계 포함 여부 명시 |

### 공통 시각 기준

무채색 중심, 얇은 경계선, 명도 차이로 구획한다. 반경은 0.625rem을 기준으로 한다. 라이트·다크 토큰을 보존하고 다크 sidebar-primary의 파란색도 유지한다. 금액은 오른쪽 정렬과 고정 숫자 폭을 사용한다.

### 반응형과 컴포넌트

데스크톱은 표 중심으로 밀도를 확보하고, 작은 화면은 메뉴를 접고 거래의 핵심 필드를 우선 표시한다. 버튼·입력·선택·대화상자·표·상태 배지는 공통 컴포넌트를 재사용한다. 정확한 서체·아이콘·간격·전환점은 실제 프리셋 확인 후 확정한다.

### 반드시 설계할 상태

첫 사용의 빈 장부, 검색 결과 없음, 로딩, 저장 중, 입력 오류, 서버 오류를 구분한다. 저장 실패 시 입력을 보존하고 재시도를 제공한다. 색상만으로 상태를 전달하지 않고 설명·아이콘을 함께 표시한다.

### 접근성과 테마

키보드 이동과 포커스 표시, 입력 라벨, 대화상자 종료 후 포커스 복귀를 검수한다. 차트는 라벨을 제공하고 양 테마에서 대비를 확인한다. 현재 렌더링이나 접근성 검증이 끝난 상태는 아니다.

## 05  주요 사용 흐름

저장 전 입력과 확정된 데이터를 구분하고, 사용자가 변경 결과를 예측할 수 있도록 설계한다.

### 일반 지출

월 선택 → 지출 추가 → 날짜·항목·금액·분류 입력 → 유효성 확인 → 저장 → 목록과 합계 갱신. 취소하면 입력 전 상태로 돌아가며 신규 거래를 남기지 않는다. 일반 지출의 귀속월은 지출일에서 기본 설정하되 수동 변경 허용 여부는 결정 항목이다.

### 입력 검증

제안 필수값은 지출일·귀속월·항목·금액·대분류다. 일반 지출은 원 단위 양수로 검증한다. 환불·취소·음수 기록은 원거래 연결 방식 또는 음수 입력 방식 중 정책 확정 후 지원한다. 기존 음수 데이터는 이관 과정에서 삭제하거나 양수로 바꾸지 않는다.

### 할부

총액·개월수·첫 귀속월 입력 → 모든 회차의 귀속월·금액 확인 → 한 번에 저장. 일부 회차만 저장되는 상태를 방지하고, 중복 제출로 같은 회차가 재생성되지 않도록 한다. 삭제 시 한 회차·남은 회차·전체 중 범위와 영향 금액을 표시한다.

### 수정과 삭제

상세 열기 → 수정 → 저장 성공 후 합계 갱신. 삭제는 대상과 범위를 확인하고 변경 이력을 남긴다. 삭제 내역 복원 가능 여부와 보존기간은 운영정책으로 정한다. 동시 수정 시 기존 변경을 조용히 덮어쓰지 않고 충돌을 알린다.

### 월별 조회

월 변경 → 월 기준 전체 지표 표시 → 분류나 카드 필터 적용. 상단 월 전체 합계와 필터 결과 합계를 구분해 표시한다. 제외 지출은 합계에서 빠진 이유와 해당 내역을 확인할 수 있게 한다.

### 카드 조회

카드 선택 → 월 사용액과 적용 기간 확인 → 상세 거래 조회. 결제기간 기준 기능을 제공할 경우 사용월 집계와 별도 이름으로 표시한다. 카드번호는 목록에서 전체를 표시하지 않는 방안을 기본으로 한다.

## 06  계산 규칙 제안

기존 계산은 관찰 사실로 보존하고, 개선 규칙은 검증과 결정 뒤 적용한다.

| 항목 | 제안 기준 |
| --- | --- |
| 월별 잔액 | 해당 월 수입 − 선택한 집계 기준의 지출. 실제 은행 잔고가 아니라 월 수지임을 표시한다. |
| 집계 제외 | 분류 이름에 의존하는 방식 대신 포함·제외 정책과 사유를 관리한다. 기존 결과와 차이를 대조한다. |
| 카드 중복 | 카드 이용과 결제대금 출금의 실제 기록 의미를 확인한 뒤 이중 집계를 방지한다. 카드내역이라는 이름만으로 제외를 확정하지 않는다. |
| 할부 배분 | 원 단위 정수 총액을 배분하고 마지막 회차에 나머지를 더한다. 예: 100,000원 / 3회 = 33,333 + 33,333 + 33,334원. |
| 할부 날짜 | 시작 연월에 회차 번호−1개월을 더한다. 예: 2026-11 시작 4회 = 11월·12월·2027년 1월·2월. |
| 기간 경계 | 윤년·월말·연말을 포함해 달력 기준으로 처리하고, 날짜와 귀속월의 역할을 구분한다. |

### 특수 계산의 취급

기존 금액_1000은 카드명에 “신한”이 포함되고 금액이 5,000 이상이며 더모아제외가 비어 있을 때 금액의 끝 세 자리를 사용한다. 실제 카드 혜택을 보장하는 공식으로 취급하지 않으며 유지 여부와 명칭을 확인한다.

예적금에는 원금·월이율·예상금액 자동입력식이 있다. 예상금액은 기존 계산과 비교하되 세후 여부·금리 변경·중도해지 반영 여부가 확정될 때까지 확정 수령액으로 표시하지 않는다.

사업 매출의 기존 공급가액은 금액 ÷ 1.1을 반올림하고 부가세는 차액으로 계산한다. 이는 기존 앱 동작의 기록이며 모든 거래에 적용되는 세무 기준으로 단정하지 않는다. 과세 유형 범위는 별도 확인한다.

## 07  데이터 설계와 이관

기존 구조를 Firestore 문서와 컬렉션으로 대응하는 논리 설계안이다. 상세 필드·인덱스·보안 규칙은 후속 설계에서 확정한다.

| 기존 구조 | 제안 대응 |
| --- | --- |
| 가계부 | 거래: 원본 ID, 장부, 지출일, 귀속월, 항목, 금액, 분류, 카드, 할부 연결 |
| 수입 | 수입 기록과 수입원: 기존 사람별 필드의 출처를 보존해 변환 |
| 지출그룹 / 소분류 | 분류: 원본 식별자와 명칭 유지, 상하위 연결은 실제 데이터 확인 |
| 가계부할부 | 할부 계약과 회차: 계약 총액, 시작월, 회차, 귀속월, 생성 거래 연결 |
| 카드 / 적금 / 매출 | 카드·예적금·매출을 각각 독립 관리하고 장부와 연결 |
| UI / Location | 화면 상태는 사용자별 상태로 분리. 위치 데이터는 필요성 확인 전 자동 이관하지 않음 |

### 이관 절차

① 원본 백업과 실제 테이블 데이터 추출 → ② 필드 대응표·변환 규칙 확정 → ③ 샘플 변환 → ④ 오류·중복·연결 누락 확인 → ⑤ 전량 이관 → ⑥ 건수와 월별·분류별·카드별 금액 대조 → ⑦ 전환 기준 충족 확인.

보고서의 레코드 수는 분석 시점의 참고값이다. 최종 이관 시점의 원본 건수와 비교한다. UUID 등 원본 식별자, 생성·수정 일시, 출처를 보존하고 재실행 시 같은 레코드가 중복 생성되지 않도록 한다.

### 오류 처리와 보존

빈 날짜·중복 ID·없는 분류 연결·비정상 연월·할부 합계 차이를 오류 목록으로 분리한다. 과거 할부를 새 규칙으로 일괄 재생성하지 않는다. 수정된 과거 값은 원본 값과 변경 이유를 추적할 수 있어야 한다.

### 민감 필드와 접근

기존 스키마에는 ID·PWD·은행 패스워드·계좌번호·카드번호·위치 관련 필드가 있다. 이는 필드 존재만 확인한 것이며 실제 값은 확인하지 않았다. 인증은 별도로 설계하고 은행 비밀번호는 자동 이관 대상에서 제외하는 안을 제안한다. 필요한 계좌·카드 정보의 저장 범위와 마스킹 기준은 확정한다.

## 10 Firebase 개발환경과 예금 조회 확장

갱신일: 2026-09-30. Firebase Hosting 선택과 개인 본인의 실제 은행·카드 내역 조회 요구를 반영했다. 현재 Markdown 문서가 최신이며 이전 Word·PDF 초안은 사용자 요청으로 삭제했다. 이 결정은 서비스 개설·결제 등록·배포를 수행했다는 뜻이 아니다.

### 채택 방향

Firebase Authentication + Cloud Firestore Standard + Firebase Hosting으로 구성한다. 인증과 Hosting은 사용자 확정 사항이다. Firestore는 대화에서 검토한 Firebase 통합 방향에 따른 DB 설계 기준으로 사용한다. 이전 Supabase·PostgreSQL 제안은 현재 기본안에서 제외한다.

| 영역 | 구성 | 상태 |
| --- | --- | --- |
| 화면 | React + TypeScript + Vite | 기획 기준 |
| 디자인 | shadcn b0 · React Aria · 등록 OKLCH 토큰 | 사용자 지정 |
| 인증 | Firebase Authentication | 확정, 로그인 수단 미정 |
| 데이터 | Firestore Standard | Firebase 통합 방향에 따른 설계 |
| 웹 호스팅 | Firebase Hosting | 확정, App Hosting과 구분 |
| 접근 제어 | Firestore Security Rules | 본인 UID 소유권 기준 |
| 개발 | Node.js LTS · pnpm · Vite | 상세 버전은 구현 시 고정, Docker 필수 아님 |
| 검증 | Vitest · Playwright · Firebase Emulator Suite | 계산·사용 흐름·보안 규칙 검증 제안 |
| 초기 요금제 | Spark 무료 범위 우선 | 실제 사용량과 확장 기능에 따라 재검토 |

기본 조회·입력은 Firebase SDK로 처리한다. 별도 상시 API 서버와 DB 서버 운영을 초기 구성에 포함하지 않는다. 폼은 React Hook Form·Zod, 라우팅은 React Router를 제안한다. 조회 캐시는 필요 범위에만 적용하며 Firebase 리스너와 중복 구독하지 않는다.

### 장부와 데이터 구조

다음은 설계안이며 아직 생성된 DB 구조가 아니다.

```text
users/{uid}
ledgers/{ledgerId}
  members/{uid}
  transactions/{transactionId}
  categories/{categoryId}
  cards/{cardId}
  installments/{installmentId}
  deposits/{depositId}
```

현재는 개인 본인 장부를 대상으로 로그인 UID와 소유자를 검증한다. 로그인 성공만으로 다른 사용자의 장부를 조회할 수 없도록 한다. 회원·역할 확장은 후속 범위로 남긴다. Google 로그인은 우선 제안이며 아직 확정하지 않는다. [보안 규칙](https://firebase.google.com/docs/firestore/security/rules-conditions)

거래는 원 단위 정수 금액, 거래일 YYYY-MM-DD, 귀속월 YYYY-MM, 카드·분류·할부 식별자, 원본 ID를 저장한다. 생성·수정 시각은 Firestore Timestamp를 사용한다. 금액 범위는 JavaScript 안전 정수 범위 안에서 명시하고 검증한다. 참조 대상의 소속 장부와 삭제 정책을 정의한다.

월별 조회와 페이지 나누기를 기본으로 하고, 전체 과거 거래를 화면 진입마다 읽지 않는다. 단순 합계는 Firestore 집계 쿼리, 분류별 분석은 필요한 월의 제한된 데이터 조회 등을 비교해 설계한다. 요약 문서를 추가하면 원거래와의 정합성·재계산 절차를 함께 정한다. [집계 쿼리](https://firebase.google.com/docs/firestore/query-data/aggregation-queries)

할부는 지원할 최대 회차 수를 명시하고, 보안 규칙 호출·요청 크기 한도 내에서 원자적 일괄 저장 또는 트랜잭션을 적용한다. 전체 성공 또는 전체 취소와 중복 생성 방지 기준을 유지한다. 원금·회차·귀속월 검증을 브라우저만 신뢰하는 구조로 만들지 않는다. 모든 회차를 안전하게 검증할 수 있는 데이터 모델과 규칙을 먼저 검증하며, 필요한 경우 서버 처리 범위를 다시 검토한다. [트랜잭션과 일괄 저장](https://firebase.google.com/docs/firestore/manage-data/transactions)

### 무료 범위와 운영

초기에는 인증·Firestore·정적 Hosting을 중심으로 Spark 한도 내에서 개발한다. Firestore 읽기·쓰기·용량과 Hosting 전송량을 각각 추적한다. 무료라는 이유로 무제한 이용이나 자동 백업을 가정하지 않는다. [Firebase 요금표](https://firebase.google.com/pricing?hl=ko)

개발·검수는 가상 또는 비식별 데이터로 진행하고 운영 프로젝트와 분리한다. 로컬 규칙 테스트에는 Emulator Suite를 사용하며 설치에 필요한 런타임은 구현 단계에서 확인한다. 일반 개발은 로컬 Vite와 개발용 Firebase 연결로 시작할 수 있다.

원본 이관은 ID 대응표와 재실행 가능한 변환 절차를 마련한다. 일일 쓰기 한도를 고려해 나누어 처리하고 월별·카드별 합계를 대조한다. 전체 내보내기·복원 기능을 기획 범위에 포함하고, 내보내기 파일의 스키마 버전·연결 관계·건수·금액을 검증한다. 앱 내보내기는 관리형 자동 백업과 구분한다.

### 개인 은행 및 카드 실제 내역 조회

사용자는 개인 본인의 실제 은행 계좌 및 카드 이용 내역 조회를 요구했다. 수동 예적금 등록과 별개의 금융 연동 기능으로 정의한다. 조회 중심으로 설계하며 이체·결제 실행은 범위에 포함하지 않는다.

| 단계 | 기능 | 처리 방향 |
| --- | --- | --- |
| 1차 예적금 관리 | 직접 등록한 예금·적금의 원금·만기·예상금액 조회 | 기존 F07 범위, Firestore에서 조회 |
| 은행 연동 | 본인 계좌의 실제 입출금 거래 내역, 잔액은 조회 항목 제안 | 대상 은행·API·개인 이용 가능 여부·인증·비용 확인 |
| 카드 연동 | 본인 카드의 실제 이용 내역 | 승인·취소·매입·청구 중 제공되는 내역의 차이를 확인 |

Firebase Hosting은 화면 배포 역할을 한다. Hosting을 선택하는 것만으로 은행 계좌 조회 기능이 제공되지는 않는다. 실제 은행·카드 조회에는 제공사가 허용하는 연동 수단과 서버 측 비밀 정보 관리가 별도로 필요하다. 사용자의 은행 비밀번호를 브라우저나 Firestore 일반 문서에 보관하는 방식은 기본안에서 제외한다.

예금 화면은 수동 입력값·은행 조회값·예상 계산값을 구분하고 마지막 갱신 시각과 조회 실패 상태를 표시한다. 은행 연동 전에는 실제 잔액이나 실시간 조회로 표현하지 않는다. 계좌 식별자, 연동 출처, 갱신 시각을 확장 가능하게 설계하되 특정 API를 미리 확정하지 않는다.

은행 연동에 서버 함수나 비밀 키 보관이 필요하면 Cloud Functions 또는 Cloud Run 등 서버 환경을 검토한다. 이 단계에서는 Blaze 결제 연결과 별도 API 비용 가능성을 확인해야 하며, 초기 Spark 무료 구성이 그대로 유지된다고 약속하지 않는다. [Firebase 요금표](https://firebase.google.com/pricing?hl=ko)

2. Firestore 필드·인덱스·보안 규칙과 할부 검증 설계를 구체화한다.

4. 금융 API의 개인 사용 자격·실데이터 지원·비용·인증·조회 기간을 검증한 뒤 연동 방식을 선정한다.

기획 문서만 갱신했으며 앱 초기화·클라우드 설정·실제 은행 연동은 수행하지 않았다.


## 11 개인 금융 내역 연동 요구사항

### 확정 범위와 제안

확정 요구는 본인의 실제 은행·카드 내역 조회다. 수동 등록이나 모의 데이터를 실제 연동 완료로 취급하지 않는다. 대상 기관, 조회 기간, 갱신 빈도는 미확정이다. 최초 구현은 은행 한 곳과 카드사 한 곳, 사용자가 누르는 새로고침 방식으로 검증하는 안을 제안한다. 자동 예약 조회는 후속 검토한다.

연동 후보는 CODEF 등 금융 데이터 API다. 공식 SDK는 은행·카드 상품과 데모·정식 서비스 신청, 추가인증 흐름을 안내한다. [CODEF 공식 SDK 안내](https://github.com/codef-io/easycodef-node/blob/master/README.md)

2026-09-30 공식 사이트 확인 결과:

- 데모는 실제 데이터로 1개월 동안 하루 100회 무료 호출을 제공한다. 일부 제휴 API는 제외된다. Sandbox는 모의 데이터다. 데모 지원을 영구 무료 운영으로 간주하지 않는다. [멤버십](https://codef.io/pricing), [FAQ](https://codef.io/cs/faq)
- 가입 화면에서 이름·이메일·비밀번호에는 필수 표시가 있고 회사정보에는 같은 표시가 없다. 다만 가입을 완료하지 않았으므로 사업자등록 없는 개인의 가입·실데이터 승인까지 검증한 것은 아니다. [회원가입](https://codef.io/account)
- 현재 유료서비스 이용약관(2025-09-11 시행) 제14조 제9항은 통합조회서비스 등 정보주체에게 데이터를 직접 교부하는 방식에 회사의 사전 동의를 요구한다. 본인만 사용하는 가계부에 대한 적용 여부와 사업자등록 없는 개인의 정식 계약 가능 여부는 제공사의 명시적 확인이 필요하다. 제8조의 개인 청구정보 언급만으로 비사업자 이용을 확정하지 않는다. [유료서비스 이용약관](https://codef.io/legal/paidService)
- 정식 요금은 별도 문의 대상이다. 대상 카드사의 지원 내역·인증 방식, 데모 종료 후 계속 이용할 자격과 비용은 미확정이다. 공식 문의처는 hd_support@hecto.co.kr / 02-6953-0257이다. [서비스 문의](https://codef.io/contact/0)

따라서 CODEF는 검토 후보로 유지한다. 개인 이용 불가라고 단정하지 않되, 현재 공개 자료만으로 개인의 지속 운영 가능을 확정하지 않는다. 제공사에 확인할 조건은 사업자등록 없는 개인, 본인 카드만 조회, 제3자 제공 없음, Firebase 기반 개인 가계부, 데모 이후 정식 사용 가능 여부 및 최소 요금이다. 문의 전송·가입·동의는 수행하지 않았다.

금융결제원 오픈뱅킹도 검토 경로지만, 개인 이용자가 서비스를 쓰는 것과 개발자가 실서비스 API를 이용하는 조건은 구분해야 한다. 운영 API 이용 자격·승인 조건을 확인하기 전 직접 연동 가능하다고 확정하지 않는다. [금융결제원 오픈뱅킹](https://openapi.kftc.or.kr/service/openBanking)

### 구성과 데이터 처리 제안

Firebase Hosting 화면 → Firebase 로그인 → 인증 토큰과 소유자를 검증하는 서버 함수 → 금융 API → 정규화·중복 검사 → Firestore 저장 → 화면 조회 순으로 구성한다. 금융 API 비밀 키는 서버에서만 관리한다. 사용자의 기관 인증·추가인증·연결 해제 흐름을 제공하고 응답이나 인증값을 일반 로그에 남기지 않는다.

수집한 원거래와 가계부에 반영한 거래를 구분한다. 기관 거래 ID를 우선 사용하고 없는 경우 기관별 식별 규칙을 정한다. 재조회 기간이 겹쳐도 중복을 만들지 않아야 한다. 카드 승인 취소·부분취소·매입 이후 변경은 원거래와 연결해 갱신한다. 조회 실패를 빈 거래 목록이나 잔액 0으로 덮어쓰지 않는다.

카드 사용액과 은행에서 출금된 카드 대금을 동시에 지출로 합산하지 않도록 분류한다. 계좌 간 이체도 소비 지출과 분리하고 애매한 거래는 사용자가 확인하게 한다. 연결 기관별 최종 성공 시각·조회 기간·실패 이유를 표시한다.

조회 데이터를 JSON 등으로 내보내고 복원 검증을 제공한다. 파일 가져오기는 연동 미지원 기관의 보완 수단일 뿐 실제 자동 조회 요구의 대체 완료로 취급하지 않는다.

### 비용과 진행 조건

Firebase 화면·수동 입력은 Spark 범위로 시작할 수 있지만 금융 API 연결에 서버 함수가 필요하므로 전체 서비스의 영구 무료 운영은 확정할 수 없다. Firebase Blaze 연결 및 금융 API 별도 요금 가능성을 분리해 산정한다. 사업자 자격이 필요한 상품인지도 제공사 기준으로 확인한다. 외부 문의·가입·계약·유료 전환은 아직 수행하지 않았다.
